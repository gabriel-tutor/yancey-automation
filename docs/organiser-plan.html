Task Management Library Review

Every file in the Task Management library: what it is, whether it is in the right place, and what it should be called. Six names have been brought into line. Fifteen were deliberately left alone, and each one says why.

What is in the library

Every document typed from what can be seen from the outside — its extension, its name, and what sits beside it. Nothing was opened. Reading the contents of a client's document library would mean sending those contents somewhere, and that is a decision to take knowingly rather than one to slip into.

The convention, as he wrote it

[Project]_[Document Name]_[YYYY-MM-DD]_[Status]_v#.#

Statuses are Draft, Review, Final and Archived. Versions run v0.1–v0.3 for working drafts, v1.0 for the first approved version, v1.1 and up for minor approved updates, v2.0 for a major revision. Every rule below is checked on every file.

✓Dates written YYYY-MM-DD, so files sortAny other date shape is reported, and an eight-digit run is refused rather than guessed at.
✓Hyphens within a phrase, underscores between sectionsSpaces become hyphens inside a section; the sections themselves stay underscore-separated.
✓No spaces, no special charactersLetters, numbers, hyphens and underscores only.
✓Document name short but descriptiveA time of day is cut out — it says when a file was made, not what it holds. Where that leaves two files with one name, both are refused, because only a person can say what each one shows.
✓No Final_Final, Latest or NewThe version number is what says which one is current.
✓Keep the version number even when marked FinalAnd a Final numbered below v1.0 is reported, since an approved version starts at v1.0.
●One place this falls short: the project prefixThe format opens with a project. Nothing in this library says which project a file belongs to, and inventing one would be worse than leaving it out, so every proposal below says the prefix was not supplied. Give a project code and it will be used.

Where things sit

The organiser proposes no moves, and that is a finding rather than an omission. Every move this library could justify would either break a Power BI refresh it cannot see, or assert how far a piece of work has got — which no file records. What it will say is when a document has no folder at all.

Why everything else stays put

What stops this going wrong

Off by default Renaming is switched off. A rename breaks every saved link, Teams tab and Power BI source pointing at the old name, so a person reads this page first.
Capped per run Even switched on, one run touches a handful of files — small enough to check by eye and undo by hand.
Never overwrites The move uses flags=0. If anything already sits on the new name the call fails rather than destroying it.
Never collides Two files that would land on the same name are both refused, not silently merged.
Never invents a status A status says whether a document is approved. Where the name doesn't carry one, the weakest — Draft — is assumed, and the assumption is shown.
Never guesses a date An eight-digit run like 04042025 is never read. Day-first and month-first disagree, and being right by luck is not being right.
Leaves Power BI alone A .pbix keeps the paths of the files it reads inside itself, where nothing outside can see them. Reports are never renamed in a sweep, and neither is a workbook sharing a report's folder or opening with a report's words.

What it can't know

The organiser can see file names, folders and timestamps. It cannot open a Power BI report to read which workbooks feed it. So it refuses where a dependency is visible from the outside — a shared folder, a shared opening — and it will miss one where a report reads from a workbook whose name looks unrelated.

Two of the files renamed above are workbooks — Metrics and the ALL STATES E-1 Table. No report opens with their words or shares their folder, so nothing here suggests a dashboard reads them. If one of them is a source for something, its old name is in the list above and the rename takes seconds to put back.
