The document organiser, and how to run it

It reads every document in the Task Management library, works out what each one actually is, and writes it a name under your convention. It changes nothing until someone switches it on. This is how it works and how to run it.

What happens to one document

Two passes. Rules decide what must never be touched; a model decides what everything else should be called. A document only reaches the model if the rules have cleared it first.

Why a model, and not a pattern

The first version matched patterns in file names. It could not have worked, and it is worth seeing why in one line.

A pattern can only rearrange the letters that are already there.

Your format opens with a project code and then a short descriptive name. Neither of those is in Metrics .xlsx. They are inside the document. So the pattern-matching version produced Metrics_2025-04-15_Draft_v0.1.xlsx — the old name with a date bolted on, wearing the convention as a costume.

Opening the file is not a shortcut around the problem. It is the problem.

Who decides what

The model never writes a file name. It fills in four blanks, and the code builds the name and checks it. That split is the whole safety argument.

The collision check runs after the model answers as well as before it. A model can land two files on one name exactly as a rule can, and when it does, both are refused rather than one being destroyed.

What actually leaves the tenant

Reading a client’s documents is a decision, so here is precisely what travels and what does not. It is one setting.

Word, Excel, PowerPoint

Text only

Unzipped on our own server. Only the text that comes out is sent, capped at about a page. The file itself never leaves.

PDFs and images

The file itself

A scan has no text layer to pull out, and an image of a dashboard can only be read by looking at it. These go to the model whole.

Power BI

Never downloaded

Reports and the workbooks feeding them are filtered out before anything is fetched. The model is never shown them at all.

Everything else

Name and folder

Anything that can’t be opened, or is too large, is named from its path and its kind — and the run says which.

Setting readContents to false stops all of it. The model then sees names, folders and file kinds only, and nothing from inside a document leaves the tenant. The naming gets worse; nothing breaks.

How to run it

It is manual only — no schedule, not published. Nothing happens in that library unless a person clicks the button.

Open
The workflow is WF-F · Organise Documents in n8n, tagged prod and documents. It has one trigger node, called Run, and it is a manual trigger — there is no schedule behind it.
Check
Look at the Config node first. Every setting lives there in one block of JSON. Confirm applyRenames and applyMoves both read false before a first run, so the run reviews and changes nothing.
Run
Press Execute workflow. It takes about 35 seconds for 21 documents — most of that is downloading them and waiting on the model. Every node should go green; a red node means the run failed rather than that it found something.
Read
Click the Summary node and open its output. That is the whole answer in one place: a headline, every proposed rename with the reason the model chose it, every assumption it made, and every refusal with the reason in full.
Publish
To turn a run into the page Yancey reads, save the run into fixtures/sharepoint/organiser-run.json and run node scripts/build-organiser-plan.mjs. The page is built from the run, never re-derived — names written by a model cannot be reproduced by rerunning anything locally.

Don’t edit the code inside the nodes.

Every node body is generated from this repository, and the next npm run build overwrites anything typed into the canvas. The judgement lives in src/naming.js, src/filenames.js and src/library.js, where it is tested. The Config node is the exception — it is there to be edited.

Every setting, and what it does

All of these sit in the Config node. The ones that change behaviour rather than tuning it are at the top.

applyRenamesfalseWhether it actually renames. Off, so a run produces a review and changes nothing. Arming it is a deliberate edit.
applyMovesfalseWhether it actually moves files. A separate switch from renaming, because it is a separate promise.

Arming it, and getting back

Renaming breaks every saved link, Teams tab and Power BI source pointing at the old path. So it is off, capped, and reversible.

Off by default

Two separate switches, both false. A run with them off is a review. Arming one is a deliberate edit to the Config node, not a click.

Five at a time

Even armed, a run touches at most five files. Read the result, run it again for the next five.

Never overwrites

The call is made with flags=0. If anything already sits on the new name, it fails rather than replacing it.

The old names are kept

Every change is recorded with what it was before. That record is the undo list — any of it can be put back by hand.

Worth being exact about one thing: this is a switch, not a missing wire. The credential can write to that library — that is what makes the tool useful. What stops a surprise rename is that the switch rests off, the cap is small, and the plan is read by a person first. If you want the stronger guarantee instead, readContents: false and leaving both switches off makes a run purely advisory.

Files renamed in the earlier pass show up again with better names. That is not a loop: the first pass gave them well-formed but mechanical names, and the agent gives them names that say what they hold. Both appear on the review page so the difference is visible rather than surprising.

When something looks wrong

The failure modes worth recognising, and what each one actually means.

  • A red node on the canvas The run failed, which is different from the organiser finding nothing to do. A run that finds nothing still finishes green and says so in the Summary.
  • “the model call failed, so the rules named what they could” The OpenAI call did not come back. The run carries on and finishes — the naming degrades, it does not break. Run it again.
  • A document named from its path rather than its contents It would not download, would not open, or was over the size cap. The Summary names which, on that document’s line.
  • A rename that failed when armed Almost always something already sitting on the new name. The call refuses rather than overwriting, and the reason comes back on that line.
  • SharePoint refusing everything A scope problem rather than a permission one, usually. There is a read-only diagnostic, WF-P · SharePoint Permissions, that compares what the token can do against what the person may do — when the second is wider, it is the scope.
